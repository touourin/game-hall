# 游戏分类独立视觉规范

这套规范用于大厅一级入口中的“游戏分类”卡片。分类视觉表达一组玩法的共同特征，不代表某一款具体游戏。

分类卡片采用统一的产品语言：**克制的赛博界面骨架 + 单主体矢量徽章**。具体游戏封面只在进入分类后的游戏列表中出现，禁止再用多张游戏封面拼成分类图片。

## 1. 视觉参考与当前配置

实际视觉以运行中的前端分类总览为准，不在 README 中重复嵌入预览图。新增分类前先运行项目，进入大厅的“游戏分类”区域，对照现有卡片的真实尺寸、主题材质、动效和响应式表现，再用本规范校准制作细节。

```bash
npm run dev
```

## 2. 分类图片如何制作

### 第一步：提炼分类语义

先写出两个并列概念，例如“布局 · 计算”或“身份 · 交锋”，再选择一个能同时覆盖这两个概念的主体。

- 主体必须代表玩法类别，而不是某一款具体游戏。
- 优先选择轮廓一眼可辨的物件、符号或操作结构。
- 不使用人物、游戏角色、文字缩写、品牌标志或现有游戏封面。
- 不用多个具体游戏物件拼贴，也不把某款游戏图标放大充当分类图。

### 第二步：先画单色轮廓

所有分类图片从 `128 × 128` 的透明 SVG 画布开始：

- `viewBox="0 0 128 128"`；
- 主体安全区约为 `14–114`，不得贴边；
- 主线宽使用 `6px`，次级结构使用 `3–5px`；
- 统一使用圆角端点和圆角连接：`stroke-linecap="round"`、`stroke-linejoin="round"`；
- 主体保持单色，允许用相同颜色的实心圆点或小面积实心结构增强识别；
- 细节数量控制在缩小到 `54px` 后仍能辨认的范围内。

先在没有底盘、光效和文字的情况下检查轮廓。如果只看轮廓仍无法判断类别，应该重画主体，而不是增加装饰。

### 第三步：应用分类色调

每个分类只有一个低饱和基准色。SVG 主体和卡片的 `--category-tone` 使用同一颜色；SVG 保持透明背景，徽章底盘和环境光由主题令牌生成，因此同一张图片可以适配四套主题。

选择新颜色时：

1. 与现有六种颜色拉开色相或明度；
2. 避免高饱和霓虹色；
3. 不使用纯红表达普通分类，以免与危险状态混淆；
4. 同步在 `GameCategoryCard.vue` 中增加对应的 `--category-tone`；
5. 在深色和浅色主题中分别检查边框、图标和标题的可辨识度。

### 第四步：放入统一徽章底盘

SVG 只负责主体轮廓。以下共同视觉由 `GameCategoryCard.vue` 统一生成，不要画进 SVG：

- 圆角方形金属/玻璃底盘；
- 内层细边框和右上状态点；
- 背景椭圆轨道、信号线与弱环境光；
- 游戏数量编号和 `CATEGORY` / `COMMUNITY` 标签；
- hover 位移、阴影和主题材质。

这样新增分类只需要设计一张主体图片，不会因为手工复制底盘而产生圆角、阴影和高光偏差。

### 第五步：在真实页面校准

不要只在 SVG 编辑器中验收。必须放进分类卡片后检查：

- 电脑端三列布局中，六个徽章大小和视觉重量是否接近；
- `390px` 手机宽度下主体是否仍然清楚；
- 图标有没有被右上角进入按钮或底部标签遮挡；
- 线条密度是否明显高于或低于已有六张图；
- 四套主题下是否出现过亮、过暗或与背景融在一起的情况；
- hover 后仍不得接近具体游戏卡片的视觉形态。

## 3. 与具体游戏图片的区别

| 项目 | 分类图片 | 具体游戏封面 |
| --- | --- | --- |
| 语义 | 一组玩法的入口 | 一款具体游戏 |
| 资源 | 单主体透明 SVG | 深色/浅色 1:1 WebP |
| 构图 | 线性符号、统一徽章底盘 | 2.5D 游戏物件产品图 |
| 色彩 | 一个低饱和分类色 | 游戏自己的完整材质配色 |
| 展示 | 一级分类卡右侧 | 二级游戏卡大图 |
| 更新 | 分类语义改变时更新 | 游戏识别物改变时更新 |

分类图片不得复制具体游戏封面，也不得通过缩小、裁切或叠放游戏封面来规避这条规则。

## 4. 页面布局规格

六个分类在电脑端使用等宽三列布局，平板使用两列，手机使用单列。所有分类卡和徽章属于同一层级，不用宽窄差异表达重要性。

### 电脑端

- 分类卡片最小高度：`230px`；
- 文案区与视觉区比例约为 `48:52`；
- 视觉区最小高度：`188px`；
- 徽章最大宽度：`132px`；
- 三列中的图标尺寸、底盘尺寸和安全区必须一致。

### 手机端

- 分类卡片最小高度：`148px`；
- 视觉区最小高度：`118px`；
- 徽章宽度约为 `78–86px`；
- 小于 `380px` 时可以隐藏描述，但分类名、游戏数量和进入意图必须保留；
- 页面和卡片不得产生横向滚动，交互热区不得小于 `44px`。

## 5. 文案规则

- 分类名称使用 `2–6` 个汉字，表达玩法范围，不使用营销口号；
- 眉题使用两个并列概念，例如“创意 · 扩展”；
- 描述说明共同的决策体验，不罗列全部游戏；
- 卡片最多展示前三款游戏名称，其余通过数量表达；
- 没有实时房间时使用“浏览游戏”，不得伪造热度；
- 社区游戏是来源型特殊分类，使用 `COMMUNITY` 标签，详情中保留社区创作者来源说明。

## 6. 新增分类的完整流程

1. 在 `frontend/src/gameCategories.ts` 的 `GameCategoryId` 增加稳定英文 ID。
2. 为官方分类补充名称、眉题、描述和全部 `gameKeys`；来源型动态分类必须写清自动收录规则。
3. 按本 README 的方法制作 `128 × 128` 透明 SVG，并放到当前目录。
4. 在本 README 的“视觉参考与当前配置”表中登记资源、主体语义和基准色，不重复嵌入预览图。
5. 在 `GameCategoryCard.vue` 导入 SVG、加入 `CATEGORY_EMBLEMS` 映射并设置 `--category-tone`。
6. 在 `gameCategories.test.ts` 中验证所有已发布游戏恰好进入一个分类。
7. 在 `GameCategoryBrowser.test.ts` 中验证分类入口、独立徽章和详情游戏卡。
8. 分别检查电脑三列、平板两列、`390px` 手机单列。
9. 检查幽蓝冷钢、曜石黑钛、月白云瓷、橘光晴釉四套主题。
10. 运行前端测试、类型检查、图标检查和生产构建。

## 7. 验收清单

提交分类视觉前必须全部通过：

1. 已在运行中的前端分类总览里与现有分类逐项对照，README 只记录可复现的方法和资源映射。
2. 图片只表达分类语义，没有复用或拼接具体游戏封面。
3. 画布、线宽、圆角端点、安全区与现有图片一致。
4. 六个或更多分类在同一行中视觉重量接近，没有某个徽章异常大或复杂。
5. `320–430px` 手机宽度无横向溢出，主体缩小后仍可辨认。
6. 四套主题中的标题、描述、数量、图标和按钮均清晰可读。
7. 分类点击后使用完整游戏卡片，社区游戏与官方游戏的卡片尺寸一致。
8. 社区游戏仍保留来源标识，不能因为视觉平级而隐藏维护边界。
9. 无人物、强霓虹、电竞盾牌、卡通边框、金币、Apple 标志和水印。
10. 测试和生产构建全部通过。
