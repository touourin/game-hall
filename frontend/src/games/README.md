# 官方游戏开发与主题适配规范

本目录只存放游戏大厅自带的官方游戏。每个游戏拥有自己的规则、状态和专属交互，但必须接入统一的模块注册、房间外壳、四套界面主题以及电脑端和手机端布局。

本规范约束的是游戏入口之后的房间与对局 UI。大厅图标与分类视觉分别遵循：

- [官方游戏图标规范](../assets/game-hall/icons/README.md)
- [官方游戏分类视觉规范](../assets/game-hall/categories/README.md)

## 1. 主题基线

当前正式主题及稳定内部 ID：

| 主题 | ID | 游戏内材质方向 |
| --- | --- | --- |
| 幽蓝冷钢 | `emerald` | 近黑军蓝哑光钢面、冷青边缘、低饱和冰蓝或青绿仪表光 |
| 曜石黑钛 | `midnight` | 曜石黑陶瓷、石墨烟玻璃、黑钛底盘、冷银精密边缘 |
| 月白云瓷 | `royal` | 月白云瓷、乳雾表面、自然铝、冷灰环境光与清晰深色文字 |
| 橘光晴釉 | `amber` | 奶油暖白、鲜润果橙、暖银结构与克制果叶绿 |

主题 ID 用于兼容用户本地设置，不得在单个游戏中改名或另建一套主题存储。

## 2. 一套结构，四套材质

每款游戏只维护一套页面结构、一套交互和一套玩法状态。四套主题必须保持以下内容一致：

- 游戏规则、空间关系和信息层级；
- 按钮位置、状态语义和触控热区；
- 棋盘、牌桌、平台或角色的轮廓；
- 动画时长、输入协议和服务端校验数据。

主题只切换背景明暗、表面材质、边缘、高光、阴影、雾层和低饱和点缀色。禁止建立 `LightGame.vue`、`DarkGame.vue` 或四份 Canvas 渲染器。

允许少量主题专属环境效果，例如幽蓝冷光、曜石冷反射、月白柔光或橘釉暖雾；这些效果必须通过主题配置启用，不能形成第二套玩法实现。

## 3. 不强行复用

只有逻辑和语义相同的部分才进入共享层：

- 房间外壳、座位、通用按钮、结果卡和标准指标可以复用平台组件；
- 围棋棋盘、扑克手牌、实时擂台、深井平台等专有交互继续留在自己的游戏目录；
- 外观相似但行为、人数或状态语义不同的组件，不得为了减少文件数量强行合并；
- 抽取共享组件前，至少确认两个使用方具有相同输入、状态和无障碍语义。

游戏目录中的 `index.ts` 是前端模块所有权边界。新游戏不得在大厅、房间或设置组件中新增按 `gameKey` 分支。

## 4. DOM/CSS 游戏界面

使用 Vue、HTML 和 CSS 构建的棋盘、牌桌或操作面板必须优先使用全局主题令牌：

- 表面：`--surface-*`、`--control-surface`、`--material-pattern`；
- 边界：`--line`、`--line-strong`、`--metal-edge`；
- 文字：`--text`、`--text-soft`、`--muted`；
- 阴影：`--shadow-contact`、`--shadow-raised`；
- 主题强调色可在游戏根元素声明一个游戏专属 CSS 变量。

禁止在整个页面上固定使用深色背景、白色文字或同一套玻璃颜色。危险、成功、阵营等语义色可以保持稳定，但必须分别检查它们在深色与两套浅色表面上的对比度。

月白云瓷不是把深色界面整体反相，也不是纯白扁平 UI。按钮、输入框、棋子和禁用态必须有明确边界；不得使用低透明度文字制造“高级感”。

## 5. Canvas 游戏界面

Canvas 游戏必须把玩法模拟和画布绘制拆开：

```text
<game>/
├── <Game>Game.vue          页面状态、输入与生命周期
├── <game>Engine.ts         确定性规则或客户端预测
├── <game>Renderer.ts       唯一 Canvas 渲染器
├── <game>Palettes.ts       共享材质到游戏对象的映射
└── <Game>Controls.vue      需要时提供手机控制器
```

这只是职责边界，不要求简单游戏机械地创建所有文件。已有小型画布可以先保留单文件；当渲染、动画和页面状态已经相互干扰时再拆分。

Canvas 适配必须满足：

1. 从 `currentTheme` 读取当前主题，并在主题切换后重绘。
2. 四套主题共用坐标、几何、碰撞和输入；场景、舞台、金属、文字与状态色必须从 `game-platform/presentation/gameThemeMaterials.ts` 取得。
3. 月白主题必须真正绘制浅色画布，不能只把外层房间改白后继续使用固定黑色画布。
4. DPR 上限、画布尺寸和坐标缩放集中处理，避免手机上模糊、拉伸或棋盘变形。
5. 角色、棋子、平台和危险物在最小手机尺寸下仍能靠轮廓辨认，不能只靠颜色。
6. Canvas 上方的 HUD、倒计时和操作提示使用 DOM 覆盖层；可点击内容不要画进 Canvas。
7. 主题切换不能改变服务端重放、种子、输入帧或结算数据。

游戏自己的调色板只保留玩法对象材质及映射，例如深井平台种类、机器人外壳和棋子阵营色。不得在每个 Canvas 游戏里重复维护整套场景背景、标准金属、正文、危险、警告与成功颜色；确实缺少的共享语义应先扩展 `GameThemeMaterials`，再由游戏调色板引用。

## 6. 电脑端与手机端

新游戏必须同时设计两端，不能先做固定桌面宽度再压缩：

- 电脑端使用模块声明的 `standard`、`wide` 或 `immersive` 房间布局；
- 320–430px 手机宽度不得出现横向滚动、裁切棋盘或被页面挤压变形；
- 主要触控热区不小于 44px，并处理 `safe-area-inset-*`；
- 实时操作游戏必须让场景和主要控制器同时可见，不能把控制器放到长画布下方；
- 横屏布局需要单独检查，不得只依赖竖屏媒体查询；
- 桌面键盘提示在触屏设备可以隐藏，但无障碍名称必须保留。

## 7. 图标、颜色与主题的关系

- 每款官方游戏必须提供 `dark` 与 `light` 两个大厅图标变体。
- 幽蓝冷钢和曜石黑钛使用相同几何的 `dark` 图标；月白云瓷和橘光晴釉使用对应 `light` 图标。
- 游戏内 UI 不需要四套不同图标，核心符号和轮廓应保持一致，只调整材质和对比度。
- 每款游戏最多选择一个低饱和专属点缀色；危险、成功和阵营色属于语义色，不计入主题点缀色。

## 8. 测试与验收

新增或重写官方游戏时至少覆盖：

- 模块已经通过 `defineBuiltinGame` 注册，且没有大厅级 `gameKey` 特判；
- 四套主题均有完整材质或令牌，不会回退到固定深色；
- 主题切换会更新画布或 DOM 样式，不会重置对局状态；
- 手机控制器位于正确容器，禁用、按下和多点触控状态正确；
- 月白主题下正文、按钮、禁用态、危险提示和棋子边界可读；
- 电脑端、390px 手机竖屏与低高度横屏没有裁切和横向溢出；
- 确定性游戏的前后端规则测试继续一致。

提交前运行：

```bash
npm --prefix frontend run test:run
npm run build
git diff --check
```

`npm run build` 已包含主题选择器与四套大厅主题的对比度检查。涉及后端规则或输入协议时，还必须运行对应的 `backend/tests`；不能用只更新前端快照的方式掩盖前后端不一致。

- [ ] 官方前后端模块均已注册，目录和能力来自模块声明。
- [ ] 幽蓝冷钢、曜石黑钛、月白云瓷、橘光晴釉均完成适配。
- [ ] 没有复制四份页面、画布或游戏逻辑。
- [ ] 没有把游戏专有逻辑塞进共享大厅组件。
- [ ] `dark`、`light` 图标符合官方图标规范。
- [ ] 电脑端、手机竖屏和低高度横屏均完成视觉与操作检查。
- [ ] 月白与橙釉两套浅色主题的按钮文字、禁用态和危险提示对比度合格。
- [ ] 测试、生产构建、主题检查与 `git diff --check` 全部通过。
