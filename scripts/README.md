# 服务重启脚本

`restart.py` 使用 Docker Compose 重新构建并重启游戏大厅。它会根据脚本自身的位置寻找仓库根目录，不依赖固定目录名；推荐把仓库放在本机的 `game-hall` 目录和服务器的 `/opt/game-hall`。

三套模型 AI 使用一致的构建开关：`ENABLE_PIKAFISH_AI`、`ENABLE_KATAGO_AI` 和
`ENABLE_DOUZERO_AI`，取值只能是 `0` 或 `1`，默认全部启用。关闭一项会跳过对应
下载、编译或运行依赖，并从最终应用镜像中省略该引擎和模型。

仓库已固定保存一套完整的 DouZero WP 三角色模型。启用 DouZero 时，构建会校验并
把模型放入应用镜像；新部署不需要手工准备权重，运行容器也不需要额外挂载权重目录。

每次运行都会先以 `--ff-only` 更新主仓库的 `main` 分支，再把所有 Git
Submodule 更新到各自配置的远端分支（`community_games` 为 `origin/main`）。
主仓库记录的子模块提交是开发、CI、复现和回滚使用的已验证基线，不限制服务器获取社区仓库的最新正式代码。

Submodule 对主项目本身是可选依赖：普通克隆未初始化它时，主项目会以零社区插件运行。生产环境执行正常更新流程时，脚本仍会初始化并更新社区仓库；拉取、构建或插件校验失败都会终止部署。使用 `--no-pull` 时则按当前检出状态构建，因此未初始化 Submodule 会得到仅含官方游戏的镜像。

源码更新后，部署分成三个阶段：

1. 构建新的应用镜像，前端插件会在这个阶段完成清单同步、类型检查和生产构建。
2. 使用新镜像读取社区发布注册表并严格加载全部已发布插件，检查清单、必需文件、Python 入口和引擎契约。
3. 只有前两步成功才替换当前应用容器，并等待健康检查。

构建或插件校验失败时，当前正在运行的应用容器不会被替换。正常更新并重启：

```bash
python3 scripts/restart.py
```

如果只想用当前已经检出的代码重建，不更新主仓库和社区仓库，仍然会执行相同的构建和插件校验：

```bash
python3 scripts/restart.py --no-pull
```

从另一台电脑远程更新服务器：

```bash
ssh root@SERVER_IP 'cd /opt/game-hall && python3 scripts/restart.py'
```

脚本必须在主仓库的 `main` 分支运行；当主仓库存在未提交的受跟踪文件，或子模块存在会被检出覆盖的本地修改时会拒绝更新。脚本会检查 Docker 和 `.env`、执行 Compose 数据库迁移依赖、只重新构建应用镜像、等待应用健康检查，并在失败时打印最近的应用日志。它不会执行 `docker compose down -v`，也不会删除 MySQL 或 Redis 数据卷。

主仓库应定期把已经在生产验证过的 `community_games` 提交更新为新的子模块基线，但社区插件发布不需要等待主仓库同步指针。需要回滚时，先检出目标主仓库与子模块提交，再使用 `--no-pull` 重建。
